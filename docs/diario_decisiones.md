# Diario de decisiones

> Cada fila describe una decisión **tomada al construir** este proyecto (D9, D16, D17 y D18 las pidió el alumno).

| # | Problema | Alternativas | Decisión | Justificación | Riesgo |
|---|---|---|---|---|---|
| D1 | ¿Cómo procesar el audio? | Audio directo al LLM / STT previo | STT previo (MAI-Transcribe-1.5 de Azure Speech) | La transcripción se registra, se valida (vacía = ininteligible) y se mide | Se pierde tono y urgencia |
| D2 | ¿Quién decide el dinero? | Solo LLM / reglas + LLM | `politicas/motor.py` decide; el agente solo coincide o escala | Reproducible y auditable; el LLM no puede "convencerse" de reembolsar | Dos fuentes de verdad (documento de políticas vs. código) |
| D3 | ¿Cómo acceder a la BD? | SQL directo / MCP | MCP con tools tipadas (14) | El LLM nunca escribe SQL; mínimo privilegio; contrato versionable | Latencia y un proceso más (stdio) |
| D4 | ¿Dónde guardar la memoria? | `MemorySaver` / SQLite / Azure SQL con paquete comunitario / saver propio | `SqlServerSaver` propio (pyodbc) | `langgraph-checkpoint-mssql` exige Python ≥ 3.12 y el entorno es 3.11; la reanudación HITL necesita persistencia real | Mantener código propio; ver `evidencia/fallas/falla_1` |
| D5 | Fuente con mayor autoridad | Imagen / BD | BD > imagen > relato | La imagen es percepción falible y puede estar alterada | BD desactualizada: se escala y **no** se corrige sola |
| D6 | Idempotencia del ticket | Sin control / clave por request | `Idempotency-Key` (o `sesion\|operación`) → `ticket_id` determinista + tabla `IdempotencyKey` | Reintentos no duplican tickets ni acciones | Colisión por claves mal generadas |
| D7 | Respuesta solo audio | Texto + audio | Solo TTS en la UI; el texto va en JSON/logs | Requisito del caso | Accesibilidad |
| D8 | `thread_id` del checkpoint | ticket / sesión | **sesión** (`SES-…`) | El ticket aún no existe al iniciar el turno 1; la memoria es por conversación | Una sesión con varios reclamos comparte hilo (se separa por ticket en el estado) |
| D9 | Identidad del cliente y notificaciones | OTP de verificación + correo al operador / sesión sin OTP y escalamiento registrado en el ticket | **Sin OTP de sesión ni correos**: el OTP existe solo como dato maestro (`autenticada_otp`, P-11); el operador atiende desde el ticket `EN_ESCALAMIENTO` y el analista aprueba por web o `hitl_cli.py` | El alumno pidió que el OTP fuera solo dato de la BD y no enviar correos; se eliminan `OtpChallenge`, `LoginTrack`, `EmailOutbox` y SMTP | Sin autenticación real del cliente: debe añadirse antes de producción |
| D10 | Texto de la respuesta hablada | Redactado por el LLM / plantillas | Plantillas con datos de la BD (`respuestas.py`) | Un monto o fecha inventados en dinero son inaceptables | Menos naturalidad |
| D11 | Ejecutar acciones | Confiar en el grafo / verificar también en la tool | La tool vuelve a verificar `AprobacionHitl.estado='APROBADA'` en BD | Defensa en profundidad si alguien invoca la tool fuera del grafo | Una consulta más por acción |
| D12 | Acceso concurrente del checkpointer | `IF NOT EXISTS`+`HOLDLOCK` / `INSERT` ignorando duplicado | `INSERT` y captura de `IntegrityError` | Evita bloqueos de rango y deadlocks; ver `falla_1` | Depende de la PK para deduplicar |
| D13 | Proveedor de IA | SDK directo en los nodos / interfaz | `ProveedorIA` (Azure o mock) | Permite pruebas deterministas sin red ni costo y cambiar de proveedor | El mock no prueba la calidad real de visión/STT |
| D14 | Esquema Liquibase | `sqlFile` / `createTable` nativo | YAML nativo (`createTable`, `addColumn`, `addForeignKeyConstraint`, `createIndex`, `insert`) con rollback por changeSet; los CHECK van como `sql` (Liquibase OSS no tiene `addCheckConstraint`) | Todo el esquema es declarativo en YAML; el runner Python lo traduce a T-SQL cuando no hay Java/Docker | El YAML con Liquibase real no se probó en este entorno; el runner se validó comparando columnas y constraints con la BD |
| D15 | Dónde viven las tablas en una BD compartida | `dbo` / usuario dedicado con esquema por defecto / esquema `multimodal` con nombres calificados | Esquema `multimodal` (`AZURE_SQL_SCHEMA`); `db.calificar` antepone el esquema a las tablas del proyecto | No contamina `dbo` (comparte BD con otros proyectos, incl. un `DATABASECHANGELOG` ajeno) y no exige cambiar el esquema por defecto de un usuario compartido | El calificador es una expresión regular sobre una lista de tablas (no un parser SQL): una tabla nueva debe añadirse a `db.TABLAS` |
| D16 | Cómo probar sin esperar 20 min | Pruebas contra Azure SQL *serverless* / SQL simulado (SQLite) + proveedor *mock* | SQL simulado y Qdrant embebido por defecto; `RUN_INTEGRACION=1` usa la BD real para una prueba marcada `integracion` | Cada flujo real tardaba ≈ 70 s (suite > 20 min); con el simulador la suite tarda ≈ 14 s y no toca servicios de pago ni compartidos | El simulador no valida T-SQL, `CHECK` ni claves foráneas: se cubre con la prueba de integración y el script de paridad del esquema |
| D17 | Dónde ejecutar Qdrant y SQL | Contenedores locales / servicios en la nube | Qdrant Cloud, Azure SQL y Azure OpenAI (Foundry, `gpt-5-mini`); se quitaron `qdrant` y `sqlserver-local` del `docker-compose.yml` | Evita mantener infraestructura local y usa los recursos del curso | Latencia (≈ 2 s por consulta SQL; la BD *serverless* se pausa y la primera conexión falla por *timeout*) y dependencia de la red |
| D18 | Cómo seguir lo que ejecuta el agente | Solo trazas/OTLP / un log legible por ejecución además de las trazas | Un fichero `temporal/<proceso>_<fecha-hora>.log` por ejecución, a nivel DEBUG (spans con sangría, nodos, tools con argumentos saneados, LLM/STT/TTS, SQL, HITL, HTTP); la consola solo muestra INFO; los subprocesos (MCP, `hitl_cli`) añaden al mismo fichero | El alumno necesita ver el paso a paso de cada corrida (p. ej. el smoke test) sin abrir Jaeger, y poder seguirlo en vivo | El log DEBUG crece rápido (MB por corrida de pruebas): `temporal/` está en `.gitignore` y se puede limpiar sin riesgo; los mensajes pasan por el enmascarado de PII |
